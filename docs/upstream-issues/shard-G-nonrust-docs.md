## 外部核查发现（本次新增，供参考）

### DOC-G1 · 文档缺陷

**位置**：`releases/v3.4.2.md` 指向 `api/rest.rs`

**现状**：`handle_plugin_api` 实际在 **`gsn-core/src/node.rs:1299`**。v3.4.2 的插件管理路由全部在 `node.rs`：`/plugins/blacklist:1351`、`/plugins/stop:1448`、`/plugins/start:1453`、unblock `:1458-1466`、`/plugins/trust:1375`。`api/rest.rs` 提到 "plugin" 仅在 `:8` 与 `:164`。

**动作**：改正路径（成本远低于把路由迁回 `api/rest.rs`）。

**验收标准**：路径与代码一致。

**建议版本**：v3.5.1（快）

### DOC-G2 · 文档缺陷（读者最易误解）

**位置**：`releases/v2.1.8.md` 的「性能指标」小节；全文另有约 20 处无测量的量化声明

**现状**：全文 **6,695 行没有一处 QPS / TPS / P99 / 守护进程吞吐基准**。唯一名为「性能指标」的小节给出「冷启动 < 1s、空闲内存 30-40 MB、包体积 2.5-10 MB」，而**同一版本的「测试验证」只有 10/10 单元测试与跨平台编译**。

分类结果：35 项量化声明中 **13 项有实测、20 项为断言/设计、2 项不清**。同类无测量声明还包括：v2.1.7 的硬件/电费/部署成本、v2.3.2 的成本倍率表、v2.3.3 的 DHT `O(log N)`（**全文无任何 DHT 复杂度测试**）、v2.4.0 的两处 `O(1)`（只验证了**相等性**、从未验证**代价**）、v2.7.5 的「延迟更低、吞吐更高」。

**动作**：二选一：① 补一次真实测量（含环境说明），② 把该节改名为**「设计目标」**。**至少为守护进程补一个端到端的吞吐/延迟基准**——这是全文最大的一块空白。另建议在 CI 中加入一个简单的基准关卡，让性能声明有可核对的来源。

**验收标准**：① 性能小节要么有可复现测量、要么明确标为设计目标；② 守护进程有端到端基准。

**建议版本**：v3.5.3

### DOC-G3 · 文档缺陷

**位置**：`releases/v2.4.1.md`「跨房间路由恒为 7 跳」；`releases/v2.4.4.md`「LRU 淘汰」

**现状**：两处已被后续版本**自己推翻**：v2.6.5 承认 `route_hops` **被硬编码为 7、忽略了真实深度**；v2.6.7 承认实际是 **LFU**。**自我更正本身是诚实的**，但只读 v2.4.x 的人会拿到已被推翻的结论。

**动作**：在早期条目上加一行「见 vX.Y.Z 更正」的注解。

**验收标准**：被推翻的条目有指向更正的注解。

**建议版本**：v3.5.3

### DOC-G4 · 文档缺陷

**位置**：未闭合项：其中 5 项处于「**沉默**」状态

**现状**：以下条目**既未被声明完成，此后再未被提及**——读者无从判断：

| 项 | 最后陈述 |
|---|---|

**验收标准**：13 项未闭合条目各有明确状态；不再有「沉默」项。

**建议版本**：v3.5.3

## 建议顺序

1. **G-3 优先**（Medium）：客户端缺 Bearer 注入点而服务端 fail-closed，**这使客户端在该路径上实际不可用**——功能性问题，非风格问题。
2. **DOC-G1 最先做**（不到 5 分钟），DOC-G2 与 DOC-G3 属文档可信度，成本低收益高。
3. **DOC-G4 是一次性补状态**，建议与 DOC-G2 同批。
4. **G-4（Python 缺钉死跨端签名向量）为 unverified**：Rust 与 JS 已有独立生成并逐字节命中的向量，Python 侧补齐即可与另两端对齐。
5. **G-5（恒真自比断言）** 属测试真伪问题，建议与「必须先验证」的测试口径复核一起做——**恒真断言会让测试计数虚高，正好干扰 582 vs 319 的判断**。
