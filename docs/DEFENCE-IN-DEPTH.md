# 纵深防御：三层，以及三层都没有覆盖的那一处

> 本文件是 C-10 的交付物之一。它的作用不是宣布三层防御已经完备，
> 而是**把每一层落在本仓库的哪个真实类型上写清楚，并把三层合起来仍然防不住的东西具名**。

## 第一层：应用级能力校验

**本仓库的真实机制是能力令牌 + 清单校验**，落在：

| 类型 | 文件 | 作用 |
|---|---|---|
| `CapabilityToken` | `crates/nau-plugin/src/capability.rs` | 一个插件**被授予**的能力集合 |
| `Capability` | 同上 | **21 个规范能力名**（`kernel:*` / `sandbox:*` / `plugin:*` / `chain:*` / `net:*`） |
| `TrustStore` / `Manifest` | `crates/nau-plugin/src/manifest.rs` | 清单签名与发布者信任 |
| `PluginGrant::require_declared` / `require_operation` | `crates/nau-plugins/src/host.rs` | **每一次调用**都按名字校验 |

**设计里写的第一层是一个 OPA/Rego 策略引擎。本仓库没有它。**

`Rego` 与 `OPA ` 在 `crates/`、`docs/` 中的检索结果是 **0 处**。
声称有这一层，就是在描述一份不在这里的软件；
而 `verify-all.mjs` 的 `defence-in-depth` 关卡**把 0 这个数字作为断言**——
**哪天真的引入了 Rego，关卡会因为「命中数不为 0」而失败，提示这句话已经过时。**

## 第二层：OS 级强制

**声明在 `crates/nau-sandbox/src/enforcement.rs`**，两种机制：

| 机制 | 约束什么 | 本构建可用性 |
|---|---|---|
| `AppArmor` | 文件与 socket 访问（按路径与 profile） | **Linux 可用；其他平台类型化拒绝** |
| `EbpFWhitelist` | 网络目的地（按地址、端口、协议） | **同上** |

**非 Linux 上是拒绝而不是跳过**，理由写在 `APPARMOR_SUPPORT` 与 `EBPF_SUPPORT` 里：
**一个报告「已应用」却没有应用的沙箱，比它自称的要弱。**

### 每条声明都带着它的前提

`PREMISES` 是三条 `(claim, depends_on, otherwise)`。**最要紧的是第一条**：

> **声明**：被约束的进程在获得 root 之后仍然被约束。
> **前提**：该进程**不持有 `CAP_MAC_ADMIN`**。**Root alone does not confer it**——
> `CAP_MAC_ADMIN` 是 `CAP_*` 集合里**独立的一个能力**，
> 而持有它的进程**可以改写约束自己的那份 profile**，那正是约束的全部。
> **否则**：该进程可以替换自己的 profile，于是**约束变成一句关于「它选择做什么」的话，
> 而不是关于「它被允许做什么」的话**。

设计的原文是「即使 Agent 拿到了管理员权限，相应规则依然有效」。
**这句话对 root 是对的，对持有 `CAP_MAC_ADMIN` 的进程是错的**，
而这个区别必须写在文本里，而不是留在读者的脑子里。

### 策略是**可替换**的，不是一次性配置

`PolicySet::apply` 增加一条、`PolicySet::replace` 整体替换，两者都返回**新的 revision**。
**一个只能在启动时设定的规则，是一个无法回答任何「启动时不知道的事」的规则。**

而**没有规则的 subject 是拒绝的**：**一条对没人写过规则的东西放行的白名单，
只是一条绕了远路的黑名单。**

## 第三层：虚拟化隔离

沙箱本身。**它的 Linux 专有机制也一样类型化拒绝**：
`SHARED_PAGE_SUPPORT`（A-09）与 `MEMORY_RECLAIM_SUPPORT`（A-10）。

## 三层合起来**仍然防不住**的：内核漏洞

**这一节是这份文件存在的理由。**

三层防御都是**策略执行**：它们决定一个进程**被允许**做什么。
而**内核漏洞不是一个权限问题**——它是一个进程做了**被允许**的事，而内核做错了。

- 第一层校验的是**能力声明**，而一个提权漏洞**不需要**超出它已声明的能力；
- 第二层约束的是**路径与目的地**，而漏洞发生在**内核处理这些路径与目的地的代码里**；
- 第三层隔离的是**命名空间与资源**，而**内核漏洞常常正是从容器里逃出去的那条路**。

**本工作区没有针对内核漏洞的通用防御。**

已有的相关能力是**观测**而不是**防御**：Agent 安全组织监控行为、审查、审判——
**它们能发现一个越权尝试，不能阻止一个 0-day。**

`XFS_IOC_SWAPEXT` 一类的越权尝试**会被能力校验拦下**——
因为那是一个**权限**问题：请求一个该插件未声明的能力，会被按名字拒绝。
而**一个只利用内核内存破坏的提权不会**：它请求的是它已经持有的能力。

**这一段不写，读者会以为三层是完备的。**
