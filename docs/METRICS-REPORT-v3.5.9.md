# AUSec 量化论断的可复现性报告（A-12 / v3.5.9）

**这份报告的作用是把「测量」与「期望」分开。**

原设计里出现了 7 个量化数字，全部被描述为「实验中」或「生产环境里」的观测，
而**没有一个给出规模、硬件、负载、基线、定义这五要素**。于是：

- 读者**无法复现**任何一个；
- 读者**无法判断**某个数字是实测还是期望——两者在原文里长得一样。

本报告对每个数字给出**本仓库能说什么**。判定只有三种：**可复现**、**不可复现（并说明缺什么）**、
**已作为设计目标明确标注**。

> **本报告本身受关卡约束。** `scripts/check-metric-claims.mjs`（v3.5.9 起为第 22 道关卡）
> 扫描 `README.md` 与 `docs/**/*.md`：任何同时含**论断动词**与**量值单位**的行，
> 必须在其上下文里带齐五要素，或被显式标注为**设计目标**。缺任一要素即关卡失败。

---

## 1. 五要素是什么，以及为什么是这五个

| 要素 | 没有它会怎样 |
|---|---|
| **规模** | 「快 3 倍」——3 个还是 30 万个对象？ |
| **硬件** | 同一份代码在笔记本与在服务器上是两个数字 |
| **负载** | 空载的延迟与满载的延迟不是同一个量 |
| **基线** | 「降低 45%」——相对**什么**降低？ |
| **定义** | 「延迟影响」是什么？测的是哪个量、怎么测、采样几次？ |

**第五条最容易被漏掉，也最致命。** A-11 的原设计写「延迟影响 45.2% → 17.3%」，
而「延迟影响」在全文中**从未被定义**——所以那两个数字**即使测过也无法被检验**，
因为它们所指的量不明。v3.5.8 因此把「同时活跃沙盒数」的**一个样本是什么**写进了
`Distribution` 的文档并用测试钉住：在活跃计数**发生变化的那一刻**取一次观测。

## 2. 逐个数字的判定

| # | 原设计论断 | 出处 | 本仓库的判定 |
|---|---|---|---|
| 1 | 安装总时长 **60 分 → 35 分** | 计划 §A-05 引 | **不可复现**。缺规模（几个镜像、多大）、硬件、负载（并发多少）、基线（相对什么）、定义（60 分测的是哪一段）。**已标注为设计目标**（`docs/DEVELOPMENT-PLAN-v3.5-v3.7-AUSec.md`）。 |
| 2 | 做种率 **1000% 健康度** | 计划 §A-07 引 | **不可复现，且前提自相矛盾**。原设计同时说「基础镜像复用率不高」——冷门镜像**恰恰做不出种**。本仓库的回应不是复现它，而是把它变成**被测量的输出**：`SeedingRatio::percent()` 返回 `Option`，**什么都没下载过的对端返回 `None`**（`0/0` 无定义），既不是 `0%` 也不是无穷。见 v3.5.4。 |
| 3 | 延迟影响 **45.2% → 17.3%** | 计划 §A-11 引 | **不可复现**。**「延迟影响」没有定义**——这是关键缺陷，不是缺数据。v3.5.8 给出了一个**有定义的**替代指标（同时活跃沙盒数分布的 p50/p99）并让调度器可测，但**没有声称复现了 45.2%→17.3%**。 |
| 4 | 后端启动开销 **`<1ms / ~2ms / ~10ms / ~100ms`** | 计划 §B-01 引 | **待测**（属 v3.6.0 的 B-01）。计划已要求「需被测量或标注为设计目标」。 |
| 5 | 快照/恢复开销 **10–100ms** | 计划 §B-0x 引 | **待测**。已在计划中标注为**设计目标而非测量**：五要素均未给出。 |
| 6 | 沙盒内运行延迟（时延敏感 vs 容忍） | 计划 §A-11 | **本仓库可测，且已测策略层**。v3.5.8 的 `Scheduler` 给出**饿死界**：容忍任务在 `aging_ticks` 内被调度，且在负载 10 与 100 000 下**界相同**。这是**算术性质**，不依赖硬件。 |
| 7 | 内存回收收益 | 计划 §A-10 | **不可在本仓库复现**。`MADV_PAGEOUT` 与 DAMON 需要 Linux 宿主 + 运行中的 guest，本仓库 CI 两者都没有（无 `/dev/kvm`，无 DAMON 内核）。v3.5.7 验证的是**策略层**（在用页永不入计划）并**如实标注**内核层未验证。 |

## 3. 本仓库**能**复现的那些，以及它们的五要素

下面这三个数字是本仓库**实测**的，且五要素齐全——它们是这份报告里唯一可以被称为「测量」的东西。

### 3.1 全工作区测试通过数

| 要素 | 值 |
|---|---|
| **规模** | 21 个 crate 的全工作区 `cargo test --workspace` |
| **硬件** | 开发者本机（Windows x86_64），`CARGO_BUILD_JOBS=2`；CI 另在 ubuntu / macos / windows 三平台各跑一遍 |
| **负载** | 单机串行，无并发测试压力 |
| **基线** | v3.5.0 之前的 1569 条 |
| **定义** | `test result: ok. N passed` 之和，`--no-fail-fast` |

**值**：1569（v3.5.0 前）→ **1677**（v3.5.8）。每个版本的增量都可逐条对上（+7 / +13 / +17 / +13 / +12 / +14 / +9 / +11 / +12）。

### 3.2 关卡与部署检查的通过数

| 要素 | 值 |
|---|---|
| **规模** | **22 道关卡** + **31 项部署检查** |
| **硬件** | 同上；部署检查起真实 daemon 并打真实 HTTP |
| **负载** | 部署检查用固定端口 4713，单实例 |
| **基线** | 21 道 + 30 项（v3.5.0–v3.5.8） |
| **定义** | `verify-all.mjs` 的 `gate(` 计数与 `deploy-local.mjs` 的 `await check(` 计数，由 `doc-counts` 关卡**从脚本数出来**并与文档比对 |

### 3.3 容忍任务的饿死界

| 要素 | 值 |
|---|---|
| **规模** | 10 000 次敏感到达，并发上限 1 |
| **硬件** | 与本机无关——**这是算术性质**，不是计时 |
| **负载** | 两种：10 与 100 000，界相同 |
| **基线** | `aging_ticks` 本身 |
| **定义** | 容忍任务从提交到被 `next_task` 选中的 tick 数 |

**值**：`≤ aging_ticks`。这个数字的特殊之处在于它**不需要硬件**——它来自
`effective = base_rank + waited / aging_ticks` 这条式子，而不是来自一次运行。

## 4. 这份报告**没有**做什么

- **没有**声称复现了原设计的任何数字。7 个里 5 个在本仓库无法复现，2 个需要在
  Linux + KVM 上测，而本仓库 CI 没有那个环境。
- **没有**把「策略层验证过」说成「机制验证过」。v3.5.6（只读共享页）与 v3.5.7（内存回收）
  的 Linux 机制是**类型检查**过的（`cargo check --target x86_64-unknown-linux-gnu`，
  并有反证：故意破坏后错误就报在那个文件里），但**从未在真实设备上运行**。
- **没有**用「实验环境」这类措辞代替五要素。本报告里每个数字要么带齐五要素，
  要么被明确判定为**不可复现**并说明缺什么。

## 5. 关卡如何防止这份报告退化

`scripts/check-metric-claims.mjs` 的规则是窄的，而且**标定过程记录在脚本里**：

- 只扫描**同时**含论断动词（降低/提升/开销/耗时/延迟/吞吐/从 X 降至/实测…）**和**
  量值单位（ms/秒/分/%/倍/…）的行；
- **跳过围栏代码块**——清单里的注释不是论断；
- **跳过含 `±` 的行**——那是代码强制的容差，不是测量；
- 五要素可以出现在**前后 8 行的段落**里，因为表格行放不下它们；
- `设计目标` / `design target` 标记视为合规——规则是**读者能分辨测量与目标**，
  而不是禁止目标。

**第一版规则会报出 23 行，其中大多数是对已发生事件的陈述**（「2 分 56 秒构建成功」）。
**一个什么都报的关卡是一个人们学会跳过的关卡**——比没有更糟，因为它还亮着绿灯。
标定后的规则报出的每一行都是真论断。

**这个关卡自己也被反证检验过。** 第一版实现里 `分\b` 用了 `\b`——而 JS 的 `\b` 是
**ASCII 词边界**，`分` 不是 `\w` 字符，所以 `60 分。` 里 `分` 后面**没有边界**，
规则**从不触发**。往文档里注入下面这一行后关卡仍然 exit 0，这才发现：

```
镜像预热把安装耗时从 60 分降至 35 分。
```

**一个永远通过的关卡比没有关卡更危险**，因为它看起来在验证。

> **这段引用本身说明了关卡的一条边界。** 一份**讨论**论断的文档必然要**提及**论断，
> 所以上面那行放在围栏代码块里——关卡跳过代码块，而代码块的用途正是引用字面量。
> 这不是漏洞：把一句真实的论断藏进代码块来规避关卡，与引用一个测试探针，在 diff 里长得不一样。
