### 0.3 与既有硬基线的**冲突点**，必须在动手前写明

| 硬基线 | 与设想的冲突 | 本计划的处理 |
|---|---|---|
| **账本精确整数与守恒** | 「代币结算」引入**第二种记账单位**（链上余额），与 `nau-ledger` 的 `Money`（minor units、精确整数）并存 | 所有链上结算**必须先经过 `nau-ledger` 的托管**，链上只是**执行**；两者对账不一致即 `fail-closed`（见 E-04） |
| **证据闸门 fail-closed** | 「信誉分同步到链上」若链不可达，是**降级**还是**拒绝** | 一律**拒绝**，不允许「链上暂时不可用就用本地信誉」（见 E-05） |
| **沙箱做不到就拒绝** | x402/L402 需要**出网**，而沙箱是**拒绝出网**的 | 支付由**宿主的签名服务**代理，沙箱内的 Agent 只持有能力令牌，**永远不持有私钥**（见 E-06） |
| **Tier 与 PluginState 既有状态与边** | 「资源提供者」是新的**主体**类型 | **不新增 Tier**：资源提供者是**已注册插件**，其状态经 `Lifecycle::transition` 的唯一转移表（见 D-03） |
| **Linux 专有机制必须类型化拒绝** | 闪电网络节点、eBPF 白名单都是 Linux 专有 | 非 Linux 上**类型化拒绝**并给出理由，**不得静默降级**（见 E-03、E-06） |
| **23 道关卡 + 54 项部署检查** | 每新增一个维度，计数 tripwire 都会亮 | 每次更新**带理由注释**，且 `doc-counts` 的 7 份文档同步（既有做法） |

### 0.4 一句话结论

> **市场机制（撮合、质押、信誉、争议、结算守恒、链上合约）已经存在；
> 而「把闲置资源当成商品计量、定价、交易」和「把结算接到比特币与以太坊」不存在。**
>
> 所以 v3.8.0 的事是**给已有的市场装上「资源」这个商品**，
> v3.9.0 的事是**给已有的结算接上链**——两件都是**接线**，不是从零造市场。

## 1. v3.8.0 族：面向 Agent 的资源市场（10 个版本）

> 沿用本仓库既有的 `com.twinsearth.sys.*` 命名与装配方式。
> 主体落点：`crates/nau-market/`（新模块）+ `crates/nau-plugins/src/plugins/`（新系统插件）+ `contracts/src/`。

### D-01 · 资源计量与商品化骨架（v3.8.0 中版本）

| | |
|---|---|
| **交付物** | `ResourceKind`（算力/内存/存储/网络/环境快照/Agent 能力六类）+ `ResourceAmount` + `ResourceOffer`，以及 `com.twinsearth.sys.resource` 系统插件 |
| **落点** | `crates/nau-market/src/resource.rs` + `crates/nau-plugins/src/plugins/resource.rs` + `host.rs` 装配 |
| **验收** | ① 六类资源**各自有单位**（CPU 毫秒 / MB·秒 / GB·秒 / 字节 / 快照摘要 / 调用次），单位不可混算；② **`Quota` 是上限、`ResourceAmount` 是商品**，两者不得互相赋值（类型不同）；③ 插件最小权限；④ 装配进部署检查 |
| **平台** | 全平台 |

> **本项的性质是「加类型」，不是「加机制」。** `Quota` 已经在 v3.6.1 存在，但它回答的是
> *「允不允许」*；市场需要回答的是 *「值多少钱」*。**把两者合并成一个类型，就是让「上限」和「价格」互相污染。**

## 2. v3.9.0 族：Agent 经济体与数字货币生态（9 个版本）

> 主体落点：`contracts/src/`（既有 4 个合约的扩展）+ `crates/nau-plugins/src/plugins/`（支付与身份插件）+ `crates/nau-node/`（签名服务）。
>
> **本族的中心原则**：**私钥永不进沙箱；链不可达一律拒绝，不降级。**

## 4. 每个版本的固定流程（与 v3.5–v3.7 相同）

1. **代码实现** —— 类型先行，落点写进计划
2. **测试** —— 每一条验收都有对应测试；**计数必须变动**（用来确认模块真的被编译）
3. **版本号 / CHANGELOG / 文档同步** —— `bump-version.mjs` + 7 份文档的计数
4. **`verify-all.mjs` 全绿** —— 23 道关卡（含 `metric-claims`）、33+ 项部署检查
5. **打 tag 发布** —— 等 **ubuntu + macOS + windows 三平台**全部通过再进入下一版

**不得回退的既有基线**（逐版检查）：
账本精确整数与守恒 · 证据闸门 fail-closed · PMB 七检查 · 沙箱做不到就拒绝 ·
Tier 与 PluginState 既有状态与边 · 关卡与部署检查计数。

## 5. 本计划**没有**承诺的东西

写清楚，比含糊更接近可交付：

1. **不承诺「世界上最大的智能体网络」。** 网络效应是结果，不是可验收项。D-10 明确要求把
   「网络效应不可用代码证明」记为边界。
2. **不承诺比特币/以太坊的「融入」。** E-03/E-06/E-07/E-08 交付的是**能力词汇、类型化拒绝、
   与已经存在的四个合约的对接**；`RGB`/`Taproot`/`Lightning`/`x402`/`L402`/`HTLC`/`ERC-8004`
   在本仓库 **0 命中**，声称支持即不可验收。
3. **不承诺代币的市场表现。** 「市值支撑」「规模数量级增长」不在工程验收范围内。
4. **不承诺收益。** 「闲置资源变现」的**机制**可以做，**收益**取决于需求侧，D-10 的冷启动
   是唯一诚实的路径。
5. **不承诺跨链桥安全。** E-08 要求把它写成**已知边界**，而不是「已缓解」。
6. **不把设计的数字当测量。** 「超卖率 50 倍」「内存下降 40.2%」「利用率 250%」——
   这些在设想里是**设计目标**，D-11/E-10 要求任何进入文档的数字**带五要素或标注为目标**，
   由 `metric-claims` 关卡强制。
