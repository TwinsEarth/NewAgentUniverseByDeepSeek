# 一切插件化架构开发方案 — NewAgentUniverseByDeepSeek V2.2.2 → V3.0.0

> 本文是 SOP「阶段一：开发方案制定」的交付物：系统架构、原理图、流程图、技术方案、技术文档。
> 它同时是一份**偏离说明**：草案里若干技术选型在本项目的构建与验证条件下无法成立，
> 本文逐条写明**为什么偏离、替代方案是什么、代价是什么**，而不是假装照着做了。
>
> 本项目的一贯规则在这里同样适用：**边界要么由代码强制执行，要么让请求失败；
> 没有证据的能力不写进声明。** 因此下文每一处「不支持」都是**类型化拒绝**，不是静默降级。

## 0. 版本映射：什么在 V2.2.2 交付，什么留给 V3.0.0

草案把「大版本 = 架构重构、中版本 = 新功能、小版本 = 独立插件、v3.0.0 = 热更新/热插拔/热兼容」。
本项目的实际情况是：**当前 V1.2.3（15 个 crate / 69,233 行 Rust）**，下一步交付 **V2.2.2**。

| 版本 | 本方案的定位 | 交付内容 |
|---|---|---|
| **V2.2.2** | 插件化内核 + 插件体系落地（对应草案的 v2.0.0 重构 + v2.1.x/v2.2.x 功能） | 插件内核（注册中心/总线/生命周期/清单/权限仲裁/黑名单/签名）、五级插件体系、PMB 内部协议、能力令牌、进程级隔离（复用 `nau-sandbox` 的强制边界）、插件认证与识别规则、第三方审核流程、测试与验证、发布 |
| **V3.0.0** | 热更新 & 热插拔 & 热兼容 | 原子切换的双缓冲热更新、热插拔依赖图、ABI 兼容适配器（加载低版本插件）、WASM Component Model 运行时、崩溃自愈与灰度回滚 |

**为什么 V2.2.2 不做热插拔**：草案自己把热插拔划归 v3.0.0（「v3.0.0 开始支持热更新&热插拔&热兼容」）。
本方案严格遵守这条线——但它把 V3.0.0 需要的**接缝全部预留并测试**（见 §9.4），
使 V3.0.0 是「接线」而不是「重写」。

## 1. 设计原则

1. **一切皆插件，但内核不是插件。** 内核只做四件事：注册、路由、仲裁、生命周期。其余全部是插件。
2. **插件不能直接调用宿主。** 唯一的通道是插件总线（PMB），因此策略执行点是**集中的、可审计的、可拦截的**。
3. **权限是令牌，不是约定。** 插件在清单里声明能力，宿主在加载时签发**能力令牌**；没有令牌的调用在总线入口就被拒绝，而不是靠插件自觉。
4. **隔离级别随信任级别递减。** 越不可信的插件，隔离越强、权限越小、配额越紧。
5. **没有证据的能力不声明。** 一个在本构建里无法强制的隔离级别，其插件**拒绝加载**，而不是降级运行。
6. **清单是签名载荷。** 版本、能力、依赖、模块摘要都在签名覆盖范围内，改一个字节即失效。

## 4. 五级插件体系

| 级别 | 前缀 | 隔离 | 权限 | 签名 | 热插拔（V3.0.0） |
|---|---|---|---|---|---|
| **T0 系统** | `com.twinsearth.sys.*` | 进程内（宿主地址空间） | 全能力 | 宿主自签（编译期内嵌摘要） | 否（仅热配置） |
| **T1 官方** | `com.twinsearth.official.*` | 独立进程 | 受限系统能力 | 官方密钥 + 清单签名 | 是 |
| **T2 认证** | `com.twinsearth.certified.*` | 独立进程 | 声明式、不超过认证等级 | 开发者签名 + **官方副签** | 是 |
| **T3 第三方** | `{publisher-domain}.*` | 独立进程 · 最严配额 | 最小集，需用户显式提权 | 仅开发者签名 | 是 |

**识别规则**：分类**仅由清单 `name` 前缀决定**，不读额外字段——因为额外的分类字段本身就是可伪造的输入。

## 5. 能力模型

能力令牌（Capability Token）在加载时签发，随插件实例生命周期存在，包含：
`plugin_id` · `granted: Vec<Capability>` · `issued_at` · `manifest_digest`（令牌绑定到具体清单字节，换清单即失效）。

| 能力组 | 例子 | T0 | T1 | T2 | T3 |
|---|---|---|---|---|---|
| 基础（所有插件） | `plugin:lifecycle:read`、`plugin:message:send`、`plugin:storage:own` | ✓ | ✓ | ✓ | ✓ |
| 网络 | `net:dht:read/write`、`net:gossip:publish/subscribe` | ✓ | 声明式 | 声明式 | **拒绝** |
| 链 | `chain:evm:read/write` | ✓ | 声明式 | 声明式 | **拒绝** |
| 经济与智能体 | `economy:settle`、`agent:card:create`、`agent:card:update`、`swarm:consensus` | ✓ | 声明式 | 审批 | **拒绝** |
| 内核 | `kernel:plugin:manage`、`kernel:policy:write`、`kernel:isolation:configure` | ✓ | **拒绝** | **拒绝** | **拒绝** |

**审批**：T0 宿主自动批准；T1 官方团队批准；T2 认证委员会批准；T3 **用户显式确认**（安装时警告 + 提权清单）。
未获批准的能力在总线入口被拒绝，并记一次违规；**违规累计 3 次 → QUARANTINED**。

## 6. 清单、签名与识别

```json
{
  "plugin": {
    "name": "com.twinsearth.official.market",
    "version": "2.2.2",
    "abi": "2.2",
    "entry": "market.bin",
    "publisher": "did:nau:…",
    "module_sha256": "…"
  },
  "capabilities": { "grant": ["plugin:message:send", "agent:card:create"] },
  "limits": {
    "memory_bytes": 268435456, "cpu_ms": 20000, "disk_bytes": 67108864,
    "max_processes": 4, "max_output_bytes": 262144
  },
  "waivers": { "network": "本主机仅回环，操作者已接受" },
  "signature": {
    "publisher_key": "…", "manifest_digest": "…",
    "sig": "…", "counter_sig": "…", "counter_key": "…"
  }
}
```

> **偏离草案（第 10 条，文档自身的修正）**：草案此处给的是 `plugin.toml`，本节一度也照抄了 TOML。
> **实现用的是 JSON**，理由是安全性的而非便利性的：签名必须覆盖**规范化**字节，而本项目已有的
> 规范化器是 JSON 的（跨 Rust/Python/JS 逐字节一致，有 10 条固定向量）。为第二种语法再写一个
> TOML 规范化器，就是让「被签的字节」与「被验的字节」多一处可能分歧的地方。
> `deny_unknown_fields` 全开：**打错一个键名是拒绝，不是被静默忽略的那一行**——
> 作者写错的那个键，正是他以为生效的那个键。
>
> `waivers` 也是**签名覆盖**的：运行时强制不了的边界必须在里面逐条写明理由，否则拒绝启动。
> 事后往清单里加豁免是不可能的，因为它会改变摘要。

**签名载荷 = 规范化清单字节**（复用 `nau-core` 已有的 canonical JSON：去 `signature`、键按码位排序、无空白、仅整数）。
校验是**四重**的，任一失败即 REFUSED：
1. `name` 前缀与声明的级别一致；
2. `manifest_digest` 与**重算**的规范化清单摘要一致；
3. `sig` 对摘要有效；
4. T1/T2 的 `counter_sig` 由受信根验证（T3 无副签，因此**永远不能**获得 T1/T2 能力）。

此外，T3 还需要**操作者显式信任其发布者公钥**——默认信任库是空的，即**未配置就不加载任何插件**。

**模块摘要绑定**：清单额外覆盖 `module_sha256`。运行前重新计算实际模块/可执行体的摘要，
不一致即拒绝——这堵住「清单合法但载荷被替换」。

## 7. 内部通信协议：PMB

**唯一通道**，四个动作：`publish(topic)` · `subscribe(topic)` · `request(target)` · `reply(corr_id)`。

```json
{
  "id": "uuid-v4",
  "corr_id": "uuid-v4 | null",
  "source": "com.twinsearth.official.market",
  "target": "com.twinsearth.sys.identity | \"broadcast\" | \"host\"",
  "capability": "plugin:message:send",
  "kind": "request | response | event",
  "topic": "market.task.settled | null",
  "payload": { },
  "issued_at": 1750000000,
  "ttl_ms": 5000,
  "priority": "critical | high | normal | low"
}
```

投递前五道检查，任一不过即**丢弃并记违规**：
1. 发送方在 RUNNING；2. 发送方令牌含 `capability`；3. `source` 与令牌绑定的 `plugin_id` 一致；
4. 目标在 RUNNING 且未被隔离；5. 速率未超配额。

**为什么不用 bincode（偏离草案）**：草案一处写 bincode、另一处写 CBOR。本项目已有**跨语言规范化 JSON**
（Rust / Python / JS 三端逐字节一致，有 10 条固定向量）。插件总线若改用 bincode，
会把「插件」锁死在 Rust 生态，并让审计日志不可读。因此 **PMB 采用规范化 JSON**：
跨语言、可审计、可复现；代价是比二进制大约 2–4 倍，用 `max_message_bytes` 上限与速率限制兜住。
CBOR 作为 V3.0.0 的可选编码预留（`Encoding` 枚举），届时同样必须过规范化与签名校验。

## 9. 隔离：PluginRuntime 端口

### 9.1 端口

```rust
pub trait PluginRuntime: Send + Sync {
    fn declares(&self) -> RuntimeCapabilities;     // 这个运行时能强制什么
    fn start(&self, spec: &PluginSpec) -> Result<PluginInstance>;
    fn call(&self, inst: &PluginInstance, req: &PmbRequest) -> Result<PmbResponse>;
    fn stop(&self, inst: PluginInstance) -> Result<()>;
}
```

**端口的存在方式与 V1.2.3 的 `SandboxExecutor` 完全一致**：每个运行时**声明自己强制什么**，
请求了它强制不了的东西就**具名拒绝**。这不是文档约定，是类型。

### 9.2 三个后端

| 运行时 | 用于 | 强制内容 | 状态 |
|---|---|---|---|
| `NativeRuntime` | T0 系统插件 | 进程内直接调用；**不做隔离**，因此 T0 仅限随内核发布的插件 | 本版实现 |
| `ProcessRuntime` | T1/T2/T3 | **经 `nau-sandbox`**：Windows Job Object（整树 kill / 内存上限 / 进程数上限）、独立工作目录、环境白名单、输出上限、超时 | 本版实现（Windows 已验证） |
| `WasmRuntime` | T1/T2/T3（V3.0.0） | Wasmtime 线性内存隔离 + epoch 抢占 + 燃料计量 | **本版不存在 → 类型化拒绝** |

### 9.3 关于 WASM 的诚实立场（重要偏离）

草案把 Wasmtime 作为插件标准格式。**本构建没有 WASM 运行时**，原因是可验证的：
`wasmtime` 及其 cranelift 依赖树不在 `Cargo.lock` 中、不在本机 registry 缓存中，
且其构建在 8 核 / 15.9 GB 的机器上与 MSRV 1.85 的约束下**无法在本会话内完成并验证**。
（`crates.io` 可达，`libloading`/`axum`/`clap`/`tokio` 已在缓存中——所以这不是网络问题，是
「引入了就必须验证」的问题。）

因此 V2.2.2 的做法是：

* 定义 `WasmRuntime` 的**端口与能力声明**，实现为**永远拒绝**并给出具名理由；
* 任何声明 `runtime = "wasm"` 的清单 → **REFUSED**，错误信息写明「本构建不含 WASM 运行时」；
* **T1/T2/T3 的隔离改由 `ProcessRuntime` 承担**，它不是安慰奖：独立进程 + Job Object 的
  内存/进程数硬上限 + 整树 kill + 独立工作目录，在「独立进程 & 独占内存」这一条上
  **强于**同进程内的 WASM 线性内存隔离（后者共享宿主地址空间与崩溃域）。

**代价必须说清楚**：进程隔离的启动开销（数十毫秒）高于 WASM 实例化；插件不能用任意语言编译到 WASM，
必须以本项目的 host ABI（stdin/stdout 上的 PMB 帧）通信。这两条都记入已知限制。

### 9.4 为 V3.0.0 预留的接缝（本版就绪并测试）

* `PluginRuntime` 端口 + `RuntimeCapabilities` 声明 + 拒绝路径（本版已用 `ProcessRuntime`/`NativeRuntime` 验证）。
* 清单的 `abi` 字段与兼容性判定函数（本版已实现并测试「主版本不匹配即拒绝」）。
* `PluginInstance` 的状态句柄与 `snapshot()/restore()` 占位（V3.0.0 的状态迁移钩子）。
* 总线路由表是**可替换的映射**，切换是单点操作（V3.0.0 原子切换的落点）。

## 10. 资源配额矩阵

| 资源 | T0 | T1 | T2 | T3 |
|---|---|---|---|---|
| CPU 时间 | 不限 | 50% 上限 | 20% 上限 | 10% 上限 |
| 内存 | 不限 | 512 MB | 256 MB | 128 MB |
| 磁盘 | 不限 | 1 GB | 512 MB | 256 MB |
| 网络 | 完整 | 声明式 | 声明式 | **拒绝** |
| 文件系统 | 完整 | 沙箱目录 | 沙箱目录 | 沙箱目录（只读） |
| 进程创建 | 允许 | 禁止 | 禁止 | 禁止 |
| 插件加载 | 允许 | 禁止 | 禁止 | 禁止 |

**「强制」与「拒绝」的界线（本构建的真实情况）**：Windows 上 Job Object 能强制**内存上限与进程数上限**
（已验证）；**CPU 时间、磁盘配额、出站网络在任何平台上都没有原语**——因此请求它们的插件
**被具名拒绝**，或在清单里显式声明豁免理由（写入审计日志）。这与 V1.2.3 的 sandbox 边界完全同一套规则。

## 13. 验证计划

**新增关卡（并入 `scripts/verify-all.mjs`）**：

| 关卡 | 检查 |
|---|---|
| `plugin-manifest` | 每个插件的清单可解析、前缀与级别一致、必填项齐全、能力名在已知集合内 |
| `plugin-signature` | 每个插件签名可验、摘要与载荷一致；**故意篡改的夹具必须被拒绝**（负向测试） |
| `plugin-tier` | 级别 → 隔离/权限矩阵的**声明与实现一致**：T3 插件不能拿到网络能力（有测试） |
| `plugin-isolation` | 恶意插件夹具（越权、越界、超配额、伪造 source）在总线入口被拒绝并记违规 |
| `plugin-no-bypass` | 源码级断言：**只有一个** `transition` 赋值点、**零处**插件直接调用宿主内部 |
| `cross-target` | 既有：Linux/macOS 类型检查（V1.2.3 新增，继续保留） |

**测试金字塔**：单元（清单/签名/令牌/状态机）→ 集成（PMB 路由、依赖图、拒绝路径）→
隔离（进程逃逸尝试、配额耗尽、伪造 source）→ 端到端（宿主加载 T0+T1+T3，跑通一次真实请求）。

**智能体测试**：用本项目自身的智能体（`nau-agent`）作为测试执行者，每个用例在进程沙箱内执行、
结果经 PMB 上报。这与草案 6.12 一致，且复用既有的 sandbox 工具面。

## 14. 与草案的偏离（逐条）

| # | 草案 | 本方案 | 理由 |
|---|---|---|---|
| 1 | Wasmtime 作为插件标准格式 | 端口保留，**本版类型化拒绝**；T1–T3 用进程隔离 | 运行时不在锁内、不在缓存中，且引入即必须验证；进程隔离在「独立进程/独占内存」上更强 |
| 2 | bincode / CBOR 编解码 | **规范化 JSON** | 已有跨语言逐字节一致的规范化器与固定向量；二进制编码会把插件锁死在 Rust 并让审计不可读 |
| 3 | Extism 插件框架 | 不引入 | 依赖 wasmtime 生态；同上 |
| 4 | opa / Rego 策略引擎 | **Rust 内建策略表 + 能力矩阵** | 引入 Rego 需新依赖与运行时；内建策略可被单元测试穷举，且拒绝路径是类型的 |
| 5 | landlock / seccomp / Firecracker | **不实现**，且不声明 | Linux 专有；本机是 Windows。Unix 后端在 V1.2.3 已被 CI 证明无法兑现声明 → **拒绝选择**，不半执行 |
| 6 | gRPC / tonic | 不实现 | 无消费方；REST + CLI + MCP 已覆盖。声明未接线的接口正是本项目审计上游时批评的行为 |
| 7 | WebSocket 实时推送 | 推迟到 V3.0.0 | 同上 |
| 8 | IPFS Bitswap / Base/Arbitrum EVM 客户端 | 不实现 | 需要真实网络与链；本版把 `chain:evm:*` 作为**能力名**存在，但**没有任何插件被授予它**，且无实现声称 |
| 9 | 26 周计划 | 分阶段交付，**V2.2.2 先交付内核 + 五级体系 + PMB + 隔离 + 认证 + 测试** | 一次交付全部 17 阶段并逐项验证在单次会话内不可能；**分阶段但每阶段可验证**优于一次性声明 |

**最后一条是整份文档的立场**：草案里有大量「将实现」的能力。本项目对上游的核心批评正是
「声明与代码不符」。因此本方案只把**已经强制或有测试断言**的东西写进插件清单与文档，
其余一律标注为未实现，并让请求它们的行为**失败**。

## 15. V3.0.0 路线（本版预留的接缝）

1. **WASM 运行时**：引入 Wasmtime（Component Model），实现 `WasmRuntime`，把 `WasmRuntime` 的拒绝替换为真实隔离；
2. **热更新**：双缓冲——新实例在独立运行时预加载并 `on_init`，通过**原子切换**路由表指针生效，旧实例优雅退出（等待在途请求，超时强杀），健康检查失败**自动回滚**；
3. **热插拔**：依赖图 + 反向依赖暂停/恢复；系统插件仍不可热插拔（仅热配置）；
4. **热兼容**：`abi` 适配器注册表，把 `2.x` 插件接口桥接到 `3.0.0` 总线；主版本不匹配时**拒绝并提示迁移**，不静默降级；
5. **安全通信**：插件间敏感消息的 X25519 + AEAD 通道（能力需声明 `crypto:channel`）。
